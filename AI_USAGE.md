## How This Project Was Actually Built

This is an important disclosure, not a formality: **the entire codebase — backend and frontend — was generated by Claude in a single conversation**, based on the attached assessment specification and a detailed system-prompt-style brief describing the required engineering standard (production-quality architecture, security, error handling, documentation, testing). There was no separate "human writes the code, AI assists" pass; a human (the candidate) provided the requirements, made the key architectural decisions listed below, reviewed the plan, and is responsible for understanding, verifying, and being able to explain every part of it before submission.

Given the assessment explicitly permits and encourages AI tools, and explicitly asks for honest disclosure rather than a fabricated manual/AI split, this report describes what actually happened rather than inventing a more traditional-looking development history.

## Decisions Made by the Candidate (Human)

Before any code was written, Claude asked, and the candidate chose:

1. **Backend framework**: NestJS (the spec's preferred option).
2. **Database**: PostgreSQL (the spec's preferred option).
3. **AI provider for testing**: left open — the abstraction was built provider-agnostic and the candidate will add a provider (OpenRouter or Groq free tier, or LM Studio locally) via the in-app AI Providers settings page.
4. **Bonus features**: Documentation Generator + Architecture Analysis, chosen as the lowest-risk pair (both reuse the same context-building and AI-client machinery as the core review engine, rather than introducing new subsystems like diff parsing or a test-generation pipeline).

These four choices shaped the entire architecture: the module boundaries, the entity schema, the provider abstraction, and which two bonus features exist at all.

## Prompting Approach

The build was driven by two inputs, both provided verbatim to Claude:

From there, generation proceeded module-by-module (auth → users → projects → files → ai-providers → reviews → chat → bonus features → frontend → docs), each built against the interfaces and entities of the modules before it, rather than as one undifferentiated dump — this is what let later modules (e.g. `reviews`, `chat`, `docs-generator`) all reuse the same `AiClient` interface and `context-builder.ts` instead of re-solving "how do I call an AI provider" three times.

## Engineering Decisions and Rationale

The reasoning behind the significant decisions is written directly into the code as comments at the point of the decision (not restating obvious code — explaining *why*), and summarized in `ARCHITECTURE.md`. The most consequential ones:

- **A single `AiClient` interface + one `OpenAiCompatibleClient` implementation**, instead of a class per vendor, because OpenAI, OpenRouter, Groq, and LM Studio/Ollama's OpenAI-compat modes all speak the same `/chat/completions` shape — this directly satisfies the "don't hardcode a provider, make adding one easy later" requirement.
- **Character-budget context building** (`reviews/context-builder.ts`) instead of naively concatenating a whole repository into a prompt, with prioritization (source files first, smaller files first) so truncation affects the least-relevant content first.
- **Keyword-based chat retrieval** rather than embeddings/RAG, isolated behind one function (`chat/context-retrieval.ts`) specifically so a future upgrade to real retrieval doesn't require touching `ChatService` — matching the spec's explicit guidance that "simple context retrieval is acceptable" and RAG should be addable later without a redesign.
- **Provider config encrypted at rest, never returned in plaintext** (`AiProvidersService.toSafeDto`), and **strict path-traversal protection on every ZIP extraction and file read** (`FilesService.safeResolve`), because the spec calls out both explicitly as security requirements, not optional hardening.
- **Failed AI calls become persisted, visible `Review` rows with a friendly error message**, not a bare 500 — so review history stays complete and the reliability requirement ("the application should remain usable" when a provider fails) is met concretely rather than just handled with a try/catch that loses the attempt.

## Trade-offs and What Was Not Verified

Per the assessment's own instruction to "make the smallest sensible engineering trade-off and document it clearly" rather than silently omit something:

- **This code was not run inside the authoring sandbox** (no reliable way to `npm install` and build/run two full Node.js applications there within a session). **This has since been superseded by real local testing**: the candidate installed both apps, ran them, uploaded and reviewed real projects, and confirmed the core features work — see the addenda below for exactly what was tested and when. This bullet is kept as an accurate record of how the project was originally generated, not as a current caveat.
- Generated documentation (README/setup/API docs) and the architecture analysis are not persisted to the database — see `ARCHITECTURE.md` → Trade-offs for why, and how to add persistence if it's wanted later.
- The JWT is stored in `localStorage` on the frontend rather than an httpOnly cookie — a known, documented trade-off for this scope (see `ARCHITECTURE.md` → Frontend Architecture).
- Automated tests cover the highest-risk paths explicitly (auth flows, project ownership enforcement, ZIP path-traversal safety) rather than every listed item in the assessment's testing checklist, in line with "do not create superficial tests merely to increase test count."



## Addendum: Post-Submission Review Pass

This section documents a second round of AI-directed work, done after initial local testing surfaced real problems. Same disclosure standard as above: **all code in this round was generated by Claude**, directed by the candidate's detailed bug reports and a follow-up requirements-review brief; nothing here was hand-written outside that process.

### What prompted this round

The candidate installed dependencies, ran both apps locally, uploaded real ZIP projects, and exercised the review/chat/docs/architecture features against a live Groq free-tier API key — genuine manual testing, not assumed to work. That testing found:
1. Large-project reviews, simple chat questions, and doc generation intermittently failing with "request too large" errors against Groq's free tier.
2. Architecture Analysis output showing raw Markdown syntax instead of rendered formatting.
3. A follow-up requirements-review request covering: full spec re-verification, responsive/theme quality, a light theme (cream-based, not plain white) with system-default + manual toggle, a truthful landing page, and documentation accuracy.

### Root cause investigation (not just a patch)

Rather than lowering one constant, the actual cause was diagnosed first: every AI-calling module (review, chat, docs, architecture) shared a single fixed context budget sized for a generous paid-tier context window, with no adaptation to what the connected provider could actually accept — and chat had a separate, compounding bug where a "no relevant file matched" case still attached several files' worth of content instead of none. Both are described in detail in `ARCHITECTURE.md`'s Change Log section. The fix (tiered budgets + adaptive shrink-and-retry, plus a stopword-aware relevance threshold for chat) addresses the mechanism, not just the symptom reported.

### Scope of the theming/responsive/landing-page work

Given the size of the full request, this pass prioritized in this order: (1) the functional context-size bugs — reproducible, clearly specified, highest impact; (2) the Architecture Analysis Markdown rendering bug; (3) a real theme system (CSS-variable-based, cream light palette, system-default with manual override, applied across every existing component via a systematic — not spot-checked — pass replacing hardcoded dark-only color utilities with theme-aware ones); (4) responsive fixes targeted at the screens most likely to break on mobile (the project workspace's fixed-height two-column panels, the top nav); (5) a landing page describing only real, implemented functionality; (6) this documentation update.

What this pass did **not** do, and why, stated plainly rather than implied as complete:
- **Not a pixel-by-pixel audit of every component at every breakpoint.** The theme refactor is systematic and the highest-traffic screens got explicit responsive fixes, but a full manual pass across desktop/tablet/mobile for every modal, form, and edge case was not performed here.
- **Still not compiled or run.** Same caveat as the original `AI_USAGE.md`: this environment cannot reliably `npm install` and build/run two full Node.js apps. All of this round's changes were written carefully against the existing, consistent codebase (same patterns, same import conventions) but have not been executed by a compiler in this session. **Run `npm install` and start both apps again before re-testing** — this is doubly important after a change this size.
- **Severity-badge and toast colors were left as fixed hex values** (not swapped per-theme) since they already read clearly on both the light and dark backgrounds — deliberate, not an oversight.

### What to re-verify

1. Re-run the exact reproduction cases that surfaced the original bugs: a large-project review, a one-line chat question ("what's the project name?"), and each doc-generation option, against the Groq free-tier key already in use.
2. Toggle Light / Dark / System in the top nav and confirm the cream light theme reads as intended, not as a re-skinned dark theme.
3. Check the project workspace (`/projects/[id]`) on an actual small screen, not just a resized desktop browser window.
4. Confirm the landing page at `/` reads accurately against what's actually implemented — it was written to only claim what exists, but it's worth a second read against the running app.

## Addendum: Third Round — Real Local-Testing Bug Reports

Same disclosure standard as the two sections above: this round's code was generated by Claude, directed by the candidate's actual server logs and observed behavior from running the app locally. This is the strongest evidence yet that the candidate is doing real verification, not just accepting generated code — these are genuine stack traces from a live run, not hypothetical concerns.

**What was reported**: a Windows-path stack trace showing `Decipheriv.final` throwing `Unsupported state or unable to authenticate data` inside `decryptSecret`, triggered from Review, Chat, and Architecture Analysis alike, plus a separate observation that the Code Explorer had regressed to showing file paths without file content.

**What was actually wrong** (diagnosed from the trace, not guessed): the decrypt call in `AiProvidersService.resolveClient()` sat outside every caller's error handling, so a key-mismatch failure (an encrypted API key that can't be decrypted with the current `JWT_SECRET`) crashed instead of being reported — exactly matching "getting internal server error only." The file-content regression is a second, unrelated issue: `FilesService` conflated "binary file" and "content missing on disk" into the same null response, and — critically — **the delivered project zip cannot contain the user's actual uploaded project data**, since that data was uploaded to the candidate's own running instance, not present in this development environment at all. If the storage directory wasn't preserved when applying the backend's updated source files (a reasonable thing to get wrong when merging a code update with a data directory), the database still remembers the files while their bytes are gone.

Both are now fixed with clear, user-facing error messages that explain the actual cause and the fix (re-add the AI provider; re-upload the ZIP), rather than either a crash or a silent blank state. See `ARCHITECTURE.md`'s Round 3 changelog entry for the technical detail.

**Update**: the candidate subsequently ran both apps locally, reproduced both bugs from real server logs (the stack traces quoted above are genuine, not illustrative), and confirmed the fixes resolved them. The generate → run locally → report real errors → fix loop this note originally called for is exactly what happened next.

## Addendum: Fifth Round — Actual Test Run Results

Prompted by the candidate pasting real `npm test` output showing 4 failing tests. Same standard as every round: AI-generated fix, human-supplied evidence, disclosed honestly — including the fact that one of the two bugs was in a test **I** wrote in Round 4, not in application code.

**What the test output actually showed**: `context-retrieval.spec.ts` failing on the "authentication" question, and `files.service.security.spec.ts` failing on the path-traversal assertion, each reported twice — initially described here as a test-runner quirk, which was wrong: Jest was scanning `backend/storage/`, where the project had been uploaded as test data, and running the copies of its own spec files found there (see the Round 6 entry in `ARCHITECTURE.md`).

**Investigation, not assumption**: rather than guessing at fixes, both root causes were confirmed empirically before changing anything — a scratch Node script installed `adm-zip` directly and proved that `addFile('../../etc/evil.txt', ...)` produces an archive containing the already-sanitized `etc/evil.txt`, never the literal traversal string; a second script reproduced the retrieval scorer's exact logic against the test fixtures to confirm the substring-matching gap. The fixes were then verified the same way — against the actual test scenarios — before being written into the real source files.

**Why this matters for the "100% working" question specifically**: the retrieval bug was a real functional gap (the Chat feature would have under-performed on very common question phrasing). The zip-traversal bug was **only in the test**, not in `FilesService` — the actual security defense was never broken. Both are worth knowing the difference between: one changed application behavior, the other changed test rigor. Neither should be waved away as "just a test issue" without checking which kind it actually was, which is what the empirical verification above was for.

**Still true**: this is the first time either of these code paths — the new prefix-matching logic, and the new raw-ZIP test fixture — has been exercised anywhere, including by me. `npm test` needs to actually be run again against this exact version before treating it as confirmed.
